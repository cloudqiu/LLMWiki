# 单实例 P99 Go 模拟：原始示例与核对

## 来源信息

- 作者、原始发表时间和链接未标注；2026-11-01 从 `raw/单实例模拟P99.md` 摄入。原文不改。
- 辅助核对：[perks quantile 官方包文档](https://pkg.go.dev/github.com/beorn7/perks/quantile)（页面显示 v1.0.1；2026-11-01 查阅）。

## 一句话概括

> 十个 worker 各处理 500 次模拟请求，用受互斥锁保护的 `quantile.Stream` 估计单进程 P50/P90/P99。

## 核心要点

- 原文第 25–57 行给 `Insert`、`Query`、`Reset` 统一加锁，符合官方文档所述 Stream 本身非线程安全的边界。
- 原文第 59–87 行用 90% 快请求、10% 慢请求构造长尾；共模拟 5000 次，不是持续运行的服务负载测试。
- 原文第 145–157 行的 HTTP middleware 仅测量 `ServeHTTP` 返回前的耗时，仍需按实际服务边界、采样和并发设计处理。

## 与官方文档的冲突和待验证

> [!warning] 原文“完整可运行”与代码不符
> 第 94–98 行 `fmt.Printf` 的格式串有 `%d`，却没有传入样本数；程序若运行会在输出中显示格式错误标记。第 97 行声称 perks 不暴露 count，但官方 `Stream.Count()` 明确存在。若输出样本数，应在锁内与三个分位一起读取 `Count()`。第 116–127 行的数值是文本示意，不能当作运行记录。

> [!warning] 误差与性能说法缺少依据
> 第 34–36、136–138 行把 `0.01`/`0.001` 写成延迟值的 ±1%/±0.1%；官方 `NewTargeted` 定义它们是**分位位置的绝对误差**。第 139–143 行的“零分配”“10 万+ QPS”和固定 100–500 摘要点没有基准或版本证据，待验证。`Reset()` 是清空当前窗口，不自动形成连续滑动窗口。

- 按原文的理想分布假设（快请求约均匀 10–50ms，慢请求约均匀 100–300ms），P99 在慢组的第 90 百分位，约 280ms；第 112、118–125 行约 200ms 只是未验证示意，不能作为稳定预期。实际 `Sleep` 时长及调度会偏离理想分布。
- 本轮未在用户环境下载依赖、编译或运行原代码；以上 API 与分位位置说明以官方包文档为准。
